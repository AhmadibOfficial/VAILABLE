# VAI-001 local foundation

## Run and verify

From this worktree only, on Linux with Python 3.11+:

```sh
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r services/api/requirements-dev.txt
# Install Chromium using your operating system's package manager (no elevated
# installation is performed by this project). The executable must be on PATH.
python3 -m uvicorn services.api.app:app --host 127.0.0.1 --port 8000
```

Open `http://127.0.0.1:8000`. In another activated terminal, from the root:

```sh
python3 scripts/verify.py
node --check apps/web/app.js
```

The existing verification script discovers API and browser tests through pytest.
Browser tests require Playwright, a Chromium executable and permission to create
loopback sockets and launch browser subprocesses. They fail rather than silently
skip when those requirements are absent. A restricted environment denying sockets
cannot verify browser acceptance. API-only diagnosis:
`python3 -m pytest -q services/api/tests/test_api.py`.

## Decisions and behavior

The blueprint's Next.js stack is a proposal. This first slice uses server-rendered
HTML, original CSS, a small dependency-free browser script and FastAPI, avoiding a
second build system. The Python frozen dataclass registry is the canonical typed
source for all 46 planned capabilities, their output limitations and priorities.
Only Merge PDF and its guest-processing capability are available. Every other
detail route displays Coming Soon and accepts no files. Search combines text and
category filters, has a live result count, and never hides the server-rendered
catalog when JavaScript is absent. The merge form requires JavaScript; no success
or download is displayed before a real PDF response.

`POST /api/merge` accepts multipart `files` in request order, 2–10 files,
5 MiB/file, 20 MiB including multipart overhead, 300 pages total and 25 MiB output.
The client rejects inputs slightly below the body cap to allow multipart overhead;
the server is authoritative. Extension, MIME and leading PDF signature must all
match; the strict parser then validates the structure. Submitted filenames are
never used as paths. Pages are appended without sorting. A single attachment
response avoids retained jobs, download tokens and cross-job retrieval routes.
Request phases are selecting, uploading/processing, succeeded/downloadable or
failed; there is no simulated progress percentage or persistent job history.

A maximum of two processing requests per process hold nonblocking capacity slots,
including upload time. Stream reads enforce the body cap without trusting
Content-Length; a 15-second upload deadline bounds incomplete requests. The
one-shot parser process has 512 MiB address-space, 8-second CPU, 12-second wall,
64-descriptor and 25 MiB file-write limits. Child stdout is an anonymous temporary
file, not an unbounded capture pipe. Cancellation kills and reaps the child before
cleanup and release. All named input files live in a private random temporary
directory; cleanup runs on success, parse errors, timeout and cancellation. No
content, filenames, passwords or parser diagnostics are logged by the app.
Abrupt host/process termination can still leave temporary input files: this is not
a certified deletion or encrypted-storage implementation.

The worker rejects encrypted PDFs, empty documents, excessively deep/large
reachable object graphs, actions, JavaScript, annotations, forms and attachments.
The implementation intentionally supports a conservative static-PDF subset.
Annotations are rejected even if benign. Only pages are copied; document-level
bookmarks, metadata, forms and digital-signature validity are not preserved.
Review merged output. No conversion, OCR, redaction, signature or AI engine exists
in this milestone; future conversions must disclose font/layout fidelity limits.

## Isolation boundary and remaining release work

This is a local development foundation, not a public upload service. Resource
limits and conservative parsing are implemented, but the worker inherits host
filesystem and network permissions. They are not a full security sandbox. Before
public uploads, use a separately confined non-root worker with no network,
read-only runtime and job-only writable mount, ingress limits/rate limiting,
encrypted ephemeral storage, crash-remnant cleanup, dependency vulnerability
review and adversarial load testing. Per-process concurrency is not a global
queue or distributed quota. A normal temporary-directory cleanup does not promise
physical erasure on disk. No account or cloud resource is created here.

All automated documents are generated synthetically in test code. Tests verify
extracted page text and geometry, encryption/active-content refusal, count/type/
size/page/output bounds, metadata removal, concurrent isolation, cleanup and
failure responses. Browser tests cover 390px and 1440px layouts, keyboard skip
navigation, search/filter/no-results, Coming Soon pages, file reordering, real
merge downloads and stale-download removal after failure. These checks are not
a complete WCAG or PDF-fidelity certification.

## Verification evidence in this worktree

`python3 scripts/verify.py` ran: the existing 8 unittest checks and Python
compilation passed; pytest reported **27 passed, 3 errors**. All three errors
occur at browser fixture setup: creating an AF_INET socket raises
`PermissionError: [Errno 1] Operation not permitted` under the task sandbox.
No browser interaction or viewport assertion ran, so mobile/desktop behavior
remains unverified here. The checks remain mandatory and are not skipped or
replaced with mock success. `node --check apps/web/app.js` passed. No Docker
image was built, no service was deployed, and no security-advisory scan ran.
